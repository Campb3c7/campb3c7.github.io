Core Concepts

Images vs Containers

🧠 Think of an image as a recipe and a container as the meal you cook from it.
An image is read-only. A container is a running instance of an image — you can have many containers from one image.

📋 Image

  • → Read-only template
  • → Built from a Dockerfile
  • → Stored in layers (efficient)
  • → Can be shared via Docker Hub
  • → Never changes once built

🚀 Container

  • → Running instance of an image
  • → Has its own writable layer
  • → Isolated process & filesystem
  • → Stopped, started, deleted
  • → Ephemeral by default

Containers vs Virtual Machines

AspectContainerVirtual Machine
Startup timeMillisecondsMinutes
SizeMegabytesGigabytes
OSShares host kernelFull guest OS
IsolationProcess-levelFull hardware-level
OverheadVery lowHigh
Key point: Containers share the host OS kernel. They are isolated via Linux namespaces and cgroups — not full virtualization. This makes them fast and lightweight.

The Dockerfile

What Is a Dockerfile?

A plain text file named Dockerfile with instructions that tell Docker how to build your image, step by step.

Each instruction creates a new layer in the image. Layers are cached — if a layer hasn't changed, Docker reuses it, making rebuilds fast.
# Start from an official base image FROM node:20-alpine # Set the working directory inside the container WORKDIR /app # Copy dependency files first (layer caching trick) COPY package*.json ./ # Install dependencies RUN npm install # Copy the rest of the source code COPY . . # Expose the port the app listens on EXPOSE 3000 # Set an environment variable ENV NODE_ENV=production # Command to run when the container starts CMD ["node", "server.js"]

Essential Dockerfile Instructions

InstructionPurposeExample
FROM Base image to build from. Always first. FROM python:3.12-slim
WORKDIR Sets the working directory for all following instructions. WORKDIR /app
COPY Copies files from host into the image. COPY src/ ./src/
RUN Executes a command during build. Creates a new layer. RUN apt-get install -y curl
ENV Sets environment variables available at runtime. ENV PORT=8080
EXPOSE Documents which port the container listens on (informational). EXPOSE 8080
CMD Default command when the container starts. Overridable. CMD ["python", "app.py"]
ENTRYPOINT Fixed command that always runs. CMD becomes its arguments. ENTRYPOINT ["gunicorn"]
CMD vs ENTRYPOINT: Use CMD for a default command that users can override. Use ENTRYPOINT when the container should always behave like a specific executable. Combine them: ENTRYPOINT = the binary, CMD = default arguments.

Image Layers — How They Stack

Each Dockerfile instruction adds a read-only layer. The container adds one writable layer on top.

5
Writable layer
Container's runtime changes (files written, logs, etc.) — lost when container is removed
4
CMD layer
CMD ["node", "server.js"]
3
COPY layer
App source code copied in
2
RUN layer
npm install — dependencies installed
1
Base layer
FROM node:20-alpine — the starting point
🧠 Layer cache tip: put instructions that change least often (installing dependencies) before instructions that change often (copying source code). This way Docker only rebuilds changed layers.

Building & Running

Building an Image

# Build an image from the Dockerfile in the current directory docker build -t my-app:latest . # -t tags the image as name:version # . is the build context (where Docker looks for the Dockerfile) # Build with a specific Dockerfile path docker build -t my-app:1.0 -f docker/Dockerfile .
FlagWhat It Does
-t name:tagName and optionally tag the image
-f pathSpecify a different Dockerfile location
--no-cacheForce a full rebuild, ignoring cached layers
--build-arg KEY=valPass build-time variables

Running a Container

# Basic run docker run my-app:latest # Run in the background (detached) with a name docker run -d --name my-container my-app:latest # Map host port 8080 → container port 3000 docker run -d -p 8080:3000 my-app:latest # Mount a host directory as a volume docker run -d -v /host/data:/app/data my-app:latest # Pass environment variables docker run -d -e DATABASE_URL=postgres://... my-app:latest
FlagWhat It Does
-dDetached mode — runs in background
-p host:containerPublish a port from container to host
-v host:containerMount a volume or bind mount
-e KEY=VALUESet environment variable
--nameAssign a name to the container
--rmAuto-remove the container when it exits
-itInteractive terminal (for shells)

Volumes — Persisting Data

A container's writable layer is deleted when the container is removed. To persist data (databases, uploads, logs), use a volume.

Named Volume (recommended)

docker volume create mydata docker run -v mydata:/app/data ...
Docker manages the storage location. Best for databases and app data.

Bind Mount

docker run -v /home/user/data:/app/data ...
Maps a specific host path. Best for development — lets you edit code on the host and see changes live.

Essential Commands

Daily Docker Commands

CommandWhat It Does
docker psList running containers
docker ps -aList all containers (including stopped)
docker imagesList all local images
docker logs my-containerView container output / logs
docker logs -f my-containerFollow (tail) live logs
docker exec -it my-container shOpen a shell inside a running container
docker stop my-containerGracefully stop a container
docker rm my-containerRemove a stopped container
docker rmi my-app:latestRemove an image
docker pull nginx:latestDownload an image from Docker Hub
docker push my-app:latestPush an image to a registry
docker inspect my-containerShow detailed container metadata (JSON)
Cleanup tip: Run docker system prune to remove all stopped containers, unused images, and dangling layers in one command. Add -a to also remove images not used by any container.

Docker Compose

Running Multiple Containers Together

Docker Compose lets you define and run a multi-container application in a single docker-compose.yml file. One command starts everything.
# docker-compose.yml services: web: build: . # build from local Dockerfile ports: - "8080:3000" environment: - DATABASE_URL=postgres://db:5432/mydb depends_on: - db db: image: postgres:16 # pull from Docker Hub volumes: - pgdata:/var/lib/postgresql/data environment: - POSTGRES_PASSWORD=secret volumes: pgdata: # named volume so DB data persists
CommandWhat It Does
docker compose up -dStart all services in background
docker compose downStop and remove containers
docker compose logs -fFollow logs from all services
docker compose buildRebuild images
docker compose psShow status of all services
docker compose exec web shOpen shell in the web service

Quick Reference — The Full Workflow

# 1. Write your Dockerfile # 2. Build the image docker build -t my-app:latest . # 3. Run a container docker run -d -p 8080:3000 --name my-container my-app:latest # 4. Check it's running docker ps # 5. View logs docker logs -f my-container # 6. Open a shell inside to debug docker exec -it my-container sh # 7. Stop and clean up docker stop my-container && docker rm my-container
🧠 The mental model: Dockerfile → docker build → Image → docker run → Container.
Everything else is managing, inspecting, or connecting those containers.
